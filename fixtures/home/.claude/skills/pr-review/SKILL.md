# PR Review

## 什么时候用

需要在一个 PR 上留下高质量 review，而不是只写 "LGTM" 或泛泛的风格建议。

## 审查顺序

1. 先看 PR 描述与改动范围是否匹配。
2. 正确性：逻辑分支、错误处理、并发与幂等。
3. 边界：空值、超长输入、时区、编码、权限。
4. 可维护性：命名、重复代码、隐藏耦合。
5. 测试：是否覆盖新增分支与回归场景。

## 评论规范

- 每条评论标明优先级：P0 阻塞 / P1 应修 / P2 建议。
- 给出具体行号与替换建议，避免只说“优化一下”。
- 不确定的地方明确写成提问，而不是断言。
